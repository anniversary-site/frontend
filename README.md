# frontend

URLUV 기념일 주문서 프런트엔드

피그마 원본을 바탕으로 구현한 기념일 웹사이트 주문서 프런트엔드입니다.

## 실행

- 개발: `npm run dev`
- 빌드: `npm run build`

## 화면 흐름

MAIN → 주문 시작하기 → 템플릿 선택 → 주문자 정보 및 수령일 → 콘텐츠 입력 → 주문 상세보기 → 접수 화면

디자인 파일: https://www.figma.com/design/LKFvy02tc2OrdE7dtLAUdf?node-id=123-821
기존 화면 순서와 페이지·Context 구조는 유지합니다. HOOKING 문구는 그대로 두고, 템플릿 이미지와 위치 안내는 API 응답을 표시하도록 연결했습니다.

## 구현 범위

- 템플릿·기념일 선택, 전화번호 자동 하이픈, 필수 입력에 따른 다음 버튼 활성화
- 메인 및 서브 문구, 템플릿의 document별 사진·영상 슬롯과 최소 사진 수 반영
- 파일 업로드·삭제, 사진 캡션·영상 제목 입력 바텀시트, API 설정에 따른 글자 수·용량 제한
- 주문서 생성·저장·조회 API 연결, 이름·전화번호 조회 및 여러 주문서 중 선택
- 주문서 ID·토큰을 localStorage에 보관하고 API에서 저장한 내용 복원
- 주문 제출·접수 결과·상태·납품 링크 표시, 요구사항 등록·목록 조회
- 모바일 768px 기준 레이아웃, 다크 모드 제외, Pretendard dynamic subset 폰트
- 업로드 대기·실패 재시도, 영상 길이·썸네일 추출, AI 문구 생성·사용하기 API 연결
- `API.js`에서 실제 백엔드와 목업 분기, `mockup.js`에서 API 15개 흐름 처리
- 토스트 2초, 바텀시트 스와이프 닫기, 키보드 가림 방지, 모션 감소 설정 지원
- 반응형 화면, 키보드 포커스, 대화상자 포커스 제어
- Vercel 사이트에서 저장소 직접 연결 완료

## 남은 작업

- 실제 백엔드와의 통합 검증은 아직 진행하지 않았습니다. 주문 접수·AI 생성·문자 발송 등 서버 동작 확인이 필요합니다.
- 완성 기념일 웹사이트 디자인·제작.
- 기간 추가 요금은 기존 프런트 계산을 유지하고 있어 서버 요금 정책과 일치하는지 확인해야 합니다.
- Vercel 실제 배포 결과 및 내부 URL 새로고침 동작 확인.

## 검증

- 타입 검사 및 프로덕션 빌드 통과: `npm run build`.
- API 15개 목업 흐름 및 요청 형식 테스트 통과: `node --test tests/api.test.mjs`.
- 실제 요청 테스트는 응답을 대체해 URL·토큰·JSON·multipart·204·서버 오류 전달을 확인했습니다. 실제 서버 호출 검증은 아닙니다.
- 브라우저 시각 검증은 컴퓨터 사용 도구가 Chrome 주소를 확인하지 못해 완료하지 못했습니다.

## 컨벤션

- `main`: Vercel에 배포되는 운영(prod) 브랜치.
- `develop`: 개발 작업의 기준 브랜치. 작업 브랜치의 변경사항을 모읍니다.
- 최신 `develop`에서 작업 브랜치를 만들어 체크아웃한 뒤 작업하고, 완료하면 `develop`에 머지해 주세요.
- 배포할 변경사항은 `develop`에서 확인한 뒤 `main`에 머지합니다.
- 작업 브랜치 이름은 `feat/기능명`, `fix/수정내용`, `docs/문서내용`, `chore/작업내용` 형식을 사용합니다.
- 커밋 메시지는 `feat: message`, `fix: message`, `docs: message`, `chore: message` 형식을 사용합니다.

작업 흐름: `develop` → 작업 브랜치 생성·체크아웃 → 작업·커밋 → `develop` 머지 → 배포 시 `main` 머지.

## 코드 스타일과 디자인 토큰

- `src/index.css`: 공통 디자인 토큰과 기본 스타일. rem 단위는 16px을 기준으로 계산합니다.
- `src/App.css`: 화면별 스타일. 색상, 간격, 모서리, 크기 및 모션은 공통 토큰을 참조합니다.
- `.prettierrc.json`: 2칸 들여쓰기, 작은따옴표, 세미콜론 생략, 최대 줄 길이 100자.
- `npm run format`: TS, TSX, CSS 등 프로젝트 코드 정렬.
- `npm run format:check`: 포맷 통일 여부 확인.

## 라우팅 구조

React Router의 `BrowserRouter`와 `Routes`/`Route`로 화면을 연결합니다.

| URL               | 화면               |
| ----------------- | ------------------ |
| `/`               | 메인               |
| `/order`          | 주문 시작          |
| `/order/load`     | 이름·전화번호 조회 |
| `/order/template` | 템플릿·기념일 선택 |
| `/order/info`     | 주문자 정보·수령일 |
| `/order/content`  | 문구·미디어 입력   |
| `/order/review`   | 주문 확인          |
| `/order/done`     | 완료               |

- `src/routes/AppRoutes.tsx`: 페이지와 URL 연결, 주문서 공통 form 레이아웃.
- `src/routes/paths.ts`: URL 상수.
- `src/pages/`: 각 화면 컴포넌트.
- `src/context/OrderContext.tsx`: 페이지에서 공통 주문서 상태에 접근하는 Context.
- 주문서 입력 상태는 페이지 이동 시 유지됩니다. 백엔드 모드에서는 새로고침 시 저장한 ID·토큰으로 API에서 복원합니다. 다른 기기에서는 이름·전화번호로 불러옵니다.
- 알 수 없는 URL은 메인으로 이동합니다.
- 배포 서버에는 `/order/*` 요청도 `index.html`을 반환하는 SPA fallback 설정이 필요합니다. 로컬 Vite 서버는 이를 지원합니다.

## TypeScript

- `src/types/order.ts`: 주문서, 첨부 파일, 페이지, 팝업, Context 공통 타입.
- `src/services/API.d.ts`: API 요청·응답 타입.
- `tsconfig.json`: strict 모드, 타입만 검사하고 별도 JS 파일을 생성하지 않음.
- `npm run typecheck`: TypeScript 타입 검사.
- `npm run build`: 타입 검사에 성공한 뒤 Vite 빌드.

## API 연결

- `src/services/API.js`: 공통 요청 및 API 함수 15개. 성공 시 `data`, 실패 시 서버의 `message`·`code`·`details` 전달.
- 목업은 메모리 기반이라 새로고침 시 초기화되며, AI는 예시 문구를 반환합니다.
- `VITE_USE_BACKEND=true`면 실제 요청, `false` 또는 미설정이면 `src/services/mockup.js` 사용.
- 실제 요청 주소는 `VITE_API_URL`에 `/api/v1`까지 포함해 설정합니다. 환경변수 값은 소문자 `true` / `false` 문자열로 구분합니다.
- `.env`는 Git에서 제외합니다. 로컬 변경 후 개발 서버 재시작, Vercel에서는 환경변수 등록 후 재배포가 필요합니다.
- 기존 `src/services/draftRepository.ts`의 IndexedDB 구현은 남아 있지만 현재 화면에서는 사용하지 않습니다.

## 이름·전화번호로 주문서 불러오기

- 기준 화면: Figma `140:239` (주문 시작하기·주문서O).
- `/order/load`: 이름·전화번호 입력 → 조회 → 여러 건이면 선택 → 작성 단계 또는 제출한 주문 확인 화면으로 이동.
- 전화번호의 하이픈은 표시용이며 API에는 숫자만 전송합니다.
- 이름·전화번호 입력 전에도 저장할 수 있고, 이 단계는 같은 브라우저에서 ID·토큰으로 이어서 작성합니다.
- 사진·영상은 선택 즉시 업로드하며, 캡션·제목은 팝업 완료 시 저장합니다.
- 조회 시 토큰을 새로 발급받아 이전 토큰은 무효가 됩니다. 문자 본인 인증은 수행하지 않습니다.
- 토큰 오류·조회 결과 없음·필수값 누락·파일 오류를 안내하며, 제출 후 수정은 요구사항 등록으로 처리합니다.

## 수령 기간과 추가 요금

- 시작일과 종료일을 고르며, 선택 범위는 달력에서 이어진 배경으로 표시됩니다.
- 최소 시작일은 API의 `minUseStartDate`를 사용하며, 기본 선택은 해당 날짜부터 7일간입니다. 새 시작일을 클릭하면 기본 7일을 선택하고, 두 번째 클릭으로 종료일을 조정합니다.
- 시작일과 종료일을 모두 포함해 7일까지 무료, 8~14일 1,000원, 15~21일 2,000원이며 이후에도 추가 7일마다 1,000원입니다.
- 달력 하단에 선택 기간과 추가 요금을 표시하고, 주문 확인 화면의 예상 금액에 합산합니다. 기본 가격·계좌는 API 설정을 사용하고, 제출 후 확정 금액은 서버의 `totalPrice`로 표시합니다.
- `src/utils/period.ts`에서 날짜 계산과 요금 정책을 관리합니다.
- 화면의 `date`·`endDate`를 API의 `useStartDate`·`useEndDate`로 변환해 저장합니다.
